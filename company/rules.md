# だんごカンパニー 全体ルール（company/rules.md）

この台帳で動くすべての役割（秘書・Ω・事業代表・作業者・先生）が守るルール。
作業を始める前に、必ずこのファイルと自分の役割ファイル（`roles/`）を読むこと。

## 1. 会社の目的

代表（としやす）が、複数のやりたい事・目標（＝事業）を同時に前へ進められるようにする。
代表の時間と余力が一番大事な資源。代表の仕事は「オーダー」「タスクの実行と一言報告」「大事な判断」だけにする。

## 2. 組織と報告ルート

```
代表（としやす）
  ⇅
秘書 … 「人」を見る。代表の状況・予定・負荷を把握し、報告を選んで届ける
  ⇅
Ω … 「事業全体」を見る。方向性を示し、余力を配分し、加速・保留・中止を提案する
  ⇅
事業代表 … 事業の管理と、作業者の仕事のチェック（ミスと方向性）
  ⇅
作業者 … 調査・タスク作成・改善案・振り返り
```

- **先生**（事業をまたぐ役割）… 代表が読んだ本とワーク結果から意見を出す。Ωに呼ばれた件で事業代表と一緒に進め方を検討し、代表の相談にも答える。意見を出すだけで、決めるのは事業代表（`roles/teacher.md`）

- 上り（報告）も下り（指示）も同じ道を通る。段を飛ばさない
- 代表への窓口は秘書だけ。Ωは秘書にだけ報告する

### 至急の例外

期限が迫った承認・予定の衝突など至急の件は、事業代表から **Ωと秘書へ同時に** 上げる。

1. 秘書はすぐ代表に届ける（遅らせない）
2. Ωは「自分で判断できる件か／代表の判断が必要な件か」を決め、判断案または理由を秘書経由で添える
3. 代表が最終判断する。Ωの判断と代表の判断を比べた結果を `company/decisions.md` に残す
4. **当面、Ωが「自分で判断できる」とした件も実行しない。判断案として記録するだけ**。方向性の一致が続いた種類の件から、代表の承認を得てΩの裁量に移す

## 3. 書き手ルール

自分の担当ファイルだけを書く。他の役割への連絡は `handoff/` か `inbox/` を通す。

| `company/owner.md` | 秘書 |

| `handoff/to-secretary.md` | Ω（通常）／事業代表（至急のみ） |
| `company/portfolio.md` `company/direction.md` | Ω |
| `company/decisions.md` | 秘書（代表の判断を記録）、Ω（自分の判断案を記録） |

### 事業フォルダ（`businesses/<事業>/`）

| ファイル | 書き手 | 中身 |
|---|---|---|
| `charter.md` | 事業代表（変更は代表の承認） | 事業計画書 |
| `plan.md` | 事業代表 | マイルストーン・事業ごとの進め方 |
| `status.md` | 事業代表 | Ωへの共通報告 |
| `orders.md` | 事業代表（依頼・差し戻し・確定）／作業者（作業中・提出の印とひとことだけ） | 依頼票 |
| `drafts/` | 作業者 | 依頼票の作業の、チェック前の成果物 |
| `tasks.md` | 作業者（事業代表のチェック後にコミット） | 今週のタスク |
| `log.md` | 作業者 | 実績 |
| `reviews/` | 作業者（事業代表のチェック後にコミット） | 週次の振り返り |
| `research/` | 作業者 | 調査メモ |
| `businesses/_template/`（事業フォルダの型） | Ω（写すのもΩ） | 新規事業の立ち上げで写す |
| 依頼票の成果物の正式な置き場所（読書の `books/` など） | 事業代表（`drafts/` から移す） | 確定した成果物。置き場所が `tasks.md` のとき（アクションプランのタスクなど）も、その分は事業代表が移す |

- `orders.md` は、事業代表と作業者の両方が書く例外のファイル（`inbox.md` の「読んだら ✅」と同じ考え方）。作業者が書いてよいのは、状態の印とひとことだけ
- 事業ごとの例外：
  - 読書 `books/`（本棚の一覧 `README.md`・本のフォルダ・`_template/`）：読書の事業代表。作業者は `drafts/` で作り、事業代表が確定時に移して本棚の一覧も直す。先生は読むだけ
  - 読書 `books/_drive-snapshot.md`：秘書（読書ノートの取り込みの控え）
  - 読書 `consults.md`（相談票）：秘書（相談を書く・届けたら ✅）／読書の事業代表（チェックを通った答えを書く）。答えの案は先生が `teacher/advice/` に作る（8-4）

## 4. 動き始めの手順

1. このファイル（`company/rules.md`）を読む
2. 自分の役割ファイル（`roles/`）を読む
3. 自分宛ての連絡（`inbox/` または `handoff/`）を読む
4. 担当ファイルを見て作業する
5. 作業が終わったら、何をしたかを担当ファイルに残し、必要なら次の役割へ `handoff/` で渡す

## 5. 判断の拠り所

- 迷ったら `company/direction.md` の方向性に照らす
- それでも決められなければ、一つ上の役割に上げる
- 方向性が合っていれば、施策（やり方）は事業ごとに自由でよい

## 6. 裁量と承認

代表の承認が必要なこと：
- 事業の追加・中止、ゴールや期限の変更
- 計画の大きな方向転換
- お金がかかること、他人が関わること

それ以外（タスクの分解、日程の組み替え、調べ物、振り返りの作成など）は各役割の裁量で進めてよい。

## 7. 記録の書き方

- 何をしたかより **「なぜ」** を残す
- 日付は `2026-09-23` 形式、時刻は24時間表記
- ログは1行1件：`- 2026-09-23 21:00 | 完了 | タスク名 | ひとこと`

## 8. 事業と定常業務

- **事業**：ゴールがあり、改善のサイクルを回すもの。同時に持てるのは **3つまで**。超えるオーダーが来たら、Ωが保留・入れ替えを提案する
- **定常業務**：決まった手順の繰り返し。秘書が担当し、事業の数には数えない

## 8-2. 新規事業の立ち上げ（定期実行を待たない。2026-09-24 代表決定で 8-3 の形にそろえた）

代表が新規事業のオーダーを書いたら、その場でルートどおりに回す。どの段も自分の担当ファイルだけを書き、段を飛ばさない。

1. **代表**：チャットでオーダーを書く（型：事業名／やりたいこと／なぜ／ゴール／かける時間／期限の目安。分からない項目は空欄でよい）
2. **秘書**：抜けている項目だけ代表に聞き、`handoff/to-omega.md` に書く
3. **Ω**：受け入れを判断する（同時に3つまで。超えるなら保留・入れ替えを提案して止める）。`company/portfolio.md`・`company/direction.md` を書く。型 `businesses/_template/` を `businesses/<事業>/` に写し、`inbox.md` に立ち上げの連絡（方向性のポイント・**先生：参加／なし**）を書く
4. **事業代表（＋先生）**：`charter.md`（ゴール・期限は案、状態は「承認待ち」）と `plan.md` を書く。「先生：参加」なら先生の意見を受けて計画に活かす。`orders.md` に最初の依頼「最初のタスクを作る」を書く
5. **作業者**：`drafts/<依頼番号>/` で最初のタスクを作り（1回15〜60分、目安時間つき）、「提出」にする
6. **事業代表**：チェックして `tasks.md` へ移し、「確定」にする。`status.md` に立ち上げの報告を書く
7. **Ω**：`status.md` を読み、概要を `handoff/to-secretary.md` に書く
8. **秘書**：代表に届け、ゴール・期限の承認をもらって `company/decisions.md` に残す。承認が出たら、事業代表が `charter.md` の状態を「進行中」にする

- **最初のタスクは、承認待ちでもカレンダーに入れてよい**。6 で確定したら、その場で秘書が今日の空き時間を見て、**余裕があれば** 今日のカレンダーに入れる（余裕がなければ翌朝の報告で並べる）
- ゴール・期限が承認で変わったら、事業代表が `charter.md`・`plan.md` を直し、必要なら最初のタスクも依頼票で作り直す
- main へのコミットは、8-3 と同じく最後に1回

## 8-3. チャットでの事業へのオーダー（2026-09-24 代表決定）

新規事業でなくても、代表がチャットで事業の作業を頼んだら（本のワークの記録など）、8-2 と同じくルートどおりにその場で回す。どの段も自分の担当ファイルだけを書く。

1. **秘書**：オーダーを受け、`handoff/to-omega.md` に書く
2. **Ω**：どの事業の件か・方向性に合うか・代表の承認がいるか・**先生がいるか** を見て、`businesses/<事業>/inbox.md` へ渡す（承認がいる件なら秘書経由で代表に聞く）
3. **事業代表（＋先生）**：`inbox.md` を読む。「先生：参加」の件は、先生の意見（`teacher/advice/`）を受けて進め方を一緒に検討し、チェック3点で確かめる。決めるのは事業代表。`orders.md`（依頼票）に依頼を書く（状態「依頼」）。完成の条件・確定後の置き場所・先生の意見も書く
4. **作業者**：`orders.md` で「依頼」「差し戻し」の件を見て、`drafts/<依頼番号>/` で作業する。終わったら状態を「提出」にする。正式な場所は触らない
5. **事業代表**：`drafts/` の成果物をチェックする（ミス・方向性・完成の条件）
   - 直す点あり → `orders.md` に理由を書いて「差し戻し」→ 4 へ戻る。2回差し戻してもまとまらなければ、`status.md` の「困っていること」に書いてΩへ上げる
   - 通過 → 正式な場所へ移し、「確定」にして `status.md` に書く（Ωへの報告）
6. **Ω**：`status.md` を読み、結果の概要を `handoff/to-secretary.md` に書く。中身を細かく理解しなくてよいが、**何が終わったかの概要は必ず知っておく**（配分・方向性の判断に使うため）
7. **秘書**：`handoff/to-secretary.md` を読み、結果を代表に届ける。代表の判断があれば `company/decisions.md` に残す

- 一つのチャットの中で、段ごとに担当を切り替えて順に動く（定期実行は待たない）。各段の連絡は短くてよい
- **main へのコミットは、事業代表の確定の後**（一つのチャットで回すときは最後に1回）。確定前の成果物を main に入れない
- 依頼票に載せるのは、チャットのオーダーとΩからの依頼だけ。毎日・毎週のタスク（「読む」、週次の振り返りなど）は今までどおり `tasks.md` で回す
- 代表への質問・確認は、どの段で出てきても秘書がまとめて聞く
- 新しいタスクが増えたら、秘書がその場で今日の空き時間を見て、余裕があれば今日のカレンダーに入れる（なければ翌朝の報告で並べる）
- 各段の型と細かい手順は役割ファイルに書く（秘書・Ωは「チャットのオーダー」、事業代表は「依頼票」、作業者は「動き始めの手順」、先生は `roles/teacher.md`）
- 先生は「先生：なし」の件でも、事業代表が意見を求めたら呼べる
- 止まっている依頼は、Ωが毎週木曜の仮案のときに見つけて書く

## 8-4. 先生への相談（Ωを通さない近道。2026-09-24 代表決定）

代表の「相談：〇〇」は作業の依頼ではなく答えがほしいだけなので、早さを優先してΩを通さない。§2 の「段を飛ばさない」の例外。

```
秘書 → 読書の事業代表 → 先生（答えの案）→ 読書の事業代表のチェック → 秘書 → 代表
```

- やりとりは相談票 `businesses/reading/consults.md`。答えの案は先生が `teacher/advice/` に作る。答え方の型とチェック3点は `roles/teacher.md`
- Ωは1件ずつの中身は見ない。`status.md` の積み上げ（相談の件数）で週1回まとめて知る
- 答えの「次の一歩」を代表がタスクにしたいと言ったら、そこからは 8-3 で回す（Ωを通す）

## 8-5. 夜の報告の事業の件は、朝の回で回す（2026-09-24 代表決定）

夜の報告（読書ノートを含む）に書かれた事業の件は、Ωの定期実行（木・日）を待たずに、翌朝の秘書の回の中で役割を切り替えて 8-3 の流れを回す。

```
6:00  秘書：夜の報告を振り分け → handoff/to-omega.md
      Ω → 事業代表（＋先生）→ 作業者 → 事業代表のチェック → Ωの概要（8-3 の 2〜6）
      秘書：朝の報告の【事業の報告】で届ける
```

- どの段も、8-3 と同じく自分の担当ファイルだけを書く
- **代表がいないとできない作業**（チャットで一緒にやるワークなど）は、朝の回では準備までにする。事業代表が依頼票を書き、作業者が代表のタスクとして `tasks.md` に足し、秘書が今日のカレンダーに入れる
- **代表の承認がいる件** は、今までどおりΩで止める。秘書が朝の報告の【確認してほしいこと】で聞く
- 6:00 の回で終わりきらなかった作業と、6:00〜10:00 に届いた報告の分は、10:00 の締めの回で続きを回し、変更の通知で届ける
- 8-4 の相談も同じ回の中で答えを作る（【先生の答え】）

## 9. 運営のリズム

| いつ | 誰が | 何を |
|---|---|---|
| 毎朝 6:00 | 秘書 | 今日の報告を代表へ。タスクをカレンダーへ入れる |
| 毎晩 | 代表 | 一言報告（自由形式）を `inbox/` へ |
| 翌朝 10:00 | 秘書 | 夜の報告の締め。届いていなければ未報告として記録 |
| 木曜 20:00 | Ω → 秘書 | 来週の仮案 |
| 日曜 20:00 | Ω → 秘書 | 来週の決定案 |
| 月末の水曜 20:00 | Ω → 秘書 | 経営会議（事業ごとの続行・加速・保留・中止の提案、新規事業の受け入れ判断） |

### 定期実行（クラウドのルーティン）

9 のリズムは、クラウドの定期実行（ルーティン）で自動で動く。2026-09-23 設定、**運用は 2026-09-24（木）開始**（代表の依頼で 9/28 から前倒し。それより前に動いた回は、何もせずに終わる）。

| 名前 | 時刻（日本時間） | 内容 |
|---|---|---|
| だんご｜秘書 朝の報告 | 毎朝 6:00 | 夜の報告ドキュメントを `inbox/` に取り込む → 夜の報告を振り分け → 事業の件は役割を切り替えて回す（8-5）→ 今日のタスクをカレンダーの空き時間に入れる → 朝の報告を届ける |
| だんご｜秘書 夜の報告の締め | 毎朝 10:00 | 6:00 以降に届いた報告を取り込み、事業の件は役割を切り替えて回し（8-5）、タスクを組み直す。届いていなければ `company/owner.md` に未報告として記録 |
| だんご｜Ω 来週の仮案 | 毎週木曜 20:00 | Ωが `meetings/weekly/` に来週の配分の仮案 → 続けて秘書が要約して届ける |
| だんご｜Ω 来週の決定案 | 毎週日曜 20:00 | Ωが金〜日の実績と代表の意見を反映した決定案 → 続けて秘書が要約して届ける |
| だんご｜Ω 経営会議 | 月末の水曜 20:00 | 毎週水曜に動き、7日後が翌月になる日（＝その月の最後の水曜）だけ実行。Ωが `meetings/monthly/` にまとめる → 続けて秘書が要約して届ける |

- 共通：毎回新しいセッションで動き、まず この `company/rules.md` と自分の役割ファイルを読む。作業結果は `main` に直接コミット・push する
- **代表への届け方**：各回の最後の出力（報告の本文）が、Claude アプリのプッシュ通知でスマホに届く
- **夜の報告の入れ方**：スマホの Google ドキュメント「夜の報告（だんごカンパニー）」の線より下に書き足すだけ。1行目に朝の報告の番号で結果（`1○ 2○ 3×`）を書き、その下は自由に書く。秘書が 6:00 と 10:00 に読み、新しく増えた分だけを `inbox/YYYY-MM-DD.md`（前日の日付）に写す。取り込み済みの内容は `inbox/_drive-snapshot.md` に保存して重複を防ぐ（ドキュメントは秘書からは消せないので、古い分は代表が好きなときに消してよい）
- **読書ノートの入れ方**：Google ドキュメント「読書ノート（だんごカンパニー）」の線より下に、読んだ本のタイトルと内容を書き足すだけ。秘書が 6:00 と 10:00 に夜の報告と一緒に取り込む（`roles/secretary.md`）
- 時刻は UTC で登録している（6:00 → `0 21 * * *`、10:00 → `0 1 * * *`、木 → `0 11 * * 4`、日 → `0 11 * * 0`、水 → `0 11 * * 3`）
- 変更・停止は claude.ai のルーティン画面から行う

## 10. 仕組みの改善

仕組みそのものの不便・改善案に気づいたら `company/backlog.md` に追記する。
